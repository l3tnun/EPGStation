# UI Parity Verification

## 概要

UI の一致確認は、ページ全体の印象ではなく、要素単位で行う。各ページは、表示要素、操作要素、状態、メニュー項目、ダイアログ、レスポンシブ表示のすべてに証跡行ができるまで「確認済み」と扱ってはいけない。

未確認、未解決、根拠のない代表確認のみの行が 1 件でもある場合、完了報告は禁止する。

## 必須手順

1. 比較対象を定義する: 現行 UI と移植/修正版 UI。
2. 修正前に UI 一致確認台帳を作る。
3. 全ページを `ページ -> セクション -> コンポーネント -> 要素 -> 状態 -> 操作 -> 操作後状態`
   まで分解する。メニュー項目、ダイアログ内ボタン、ページネーションボタン、アイコンのみボタン、レスポンシブ時だけ出る UI も個別の要素行にする。
4. 両方の UI で証跡を取る: ページ全体スクショ、要素単位スクショ、DOM/アクセシビリティ情報。
5. 文言、アイコン、順序、件数、位置、サイズ、余白、色、フォント、disabled/selected/focus/hover、aria-label、role、操作結果を比較する。
6. サブエージェントにも同じスクショを見せ、同じ観点で UI 差分レビューを実施させる。
7. 差分を再現し、台帳に記録してから修正する。
8. 修正後、必ず再度スクショを撮り、現行 UI のスクショと同じ条件、同じ操作、同じ観点で再比較する。
9. 修正後の再比較もサブエージェントに実施させる。
10. 1 箇所を直したら、同種 UI を `rg` で横断検索する。
11. 最終報告では件数を出す。未確認、未解決、差分ありが 0 件でない限り、完了と言ってはいけない。

## 要素の定義

この skill における「要素」とは、ユーザーが認識、操作、または比較できる UI の最小単位を指す。DOM ノード単位とは限らないが、複合コンポーネントを 1 要素として済ませてはいけない。

要素分解は「ユーザーが個別に視認、説明、操作対象として指差せる単位」まで分ける。1 つの要素が 2 つ以上のテキスト、アイコン、操作、状態表示を含む場合は分割する。迷った場合は細かい側に倒す。1 要素 =
1 主張、つまり 1 つのテキスト、アイコン、操作、状態を原則にする。

要素には最低限、以下を含める。

- 表示テキスト、ラベル、補助文、件数、日時、ステータス表示
- 画像、サムネイル、no image 表示、アイコン
- ボタン、リンク、アイコンボタン、入力欄、チェックボックス、セレクト、タブ、スイッチ
- メニューを開くボタン、メニュー内の各項目、区切り線、破壊的操作の表示
- ダイアログのタイトル、本文、各アクションボタン、閉じる操作
- ページネーションの prev / next / page number / ellipsis / 件数表示
- loading、empty、error、disabled、selected、focused、hover、success、failure の状態表示
- desktop/tablet/mobile で出現、消失、置換される UI

例: 「録画済みアイテム」は 1 行で確認済みにしてはいけない。サムネイル、タイトル、説明、日時、ステータス、protect 表示、メニューボタン、メニュー項目ごとに台帳行を分ける。

例: 「録画済みアイテムメニュー」は 1 行で確認済みにしてはいけない。メニューを開く操作、`rule`、`search`、`protect/unprotect`、`encode`、`delete`
の各項目、各アイコン、各押下結果を別行にする。現行 UI にない `play TS` のような項目が出る場合は差分として記録する。

## 台帳の必須項目

Markdown または CSV で、要素/状態/操作ごとに 1 行の台帳を作る。最低限、以下の列を持たせる。

- ページ
- viewport: desktop/tablet/mobile
- セクション
- コンポーネント
- 要素
- 状態
- 操作
- 現行 UI の証跡パス
- 修正版 UI の証跡パス
- 修正後 UI の証跡パス
- サブエージェント初回レビュー結果パス
- サブエージェント再レビュー結果パス
- 自分の指摘件数
- サブエージェントの指摘件数
- 再比較ループ番号
- サブエージェント指摘の採用/却下
- サブエージェント指摘を却下した理由と根拠パス
- 現行 UI の期待表示/動作
- 修正版 UI の実際表示/動作
- ステータス: `未着手`, `現行確認済み`, `修正版確認済み`, `差分あり`, `修正中`, `修正済み(未再確認)`, `再確認済み`,
  `未確認`, `未解決`, `対象外`
- 備考

禁止する台帳表現:

- 「ページ確認済み」
- 「だいたい近い」
- 「代表アイテム」
- 「上と同じ」
- 「主要操作のみ」

## ページと状態の発見

確認対象ページは手作業で思いついたものだけにしてはいけない。以下を使って到達可能なページと状態を列挙する。

- route 定義
- サイドナビ / ヘッダナビ / フッタナビ
- 一覧から詳細へのリンク
- メニュー項目からの遷移
- 検索結果、フィルタ結果、編集画面、確認画面
- 権限、データ件数、通信状態、録画状態による条件付き表示

発見した route、状態、状態生成条件を台帳または別ファイルに記録する。現在の手元データで見えない状態も削除せず、必要な fixture、mock、API 条件を記録する。

route 定義から抽出した route 一覧、ナビから到達できるページ一覧、一覧/詳細/メニュー/検索結果から遷移できるページ一覧を作り、相互に突合する。ナビに出ない route、動的 route、query
string、tab、filter、sort、modal route も削除せず台帳化する。

動的 route は、実データまたは fixture で代表 ID を用意し、正常、存在しない ID、権限なし、読み込み失敗の状態を確認する。

## Component Family 代表確認

ユーザー承認済みの高速化モードでは、同一 React コンポーネント、同一 CSS module、同一 props
contract、同一操作結果で描画される UI を `component family` として代表確認できる。

代表確認は確認省略ではない。代表証跡に紐付ける行は、代表 rowIds、代表現行 UI 証跡、代表修正版 UI 証跡、DOM/a11y
summary、`rg` 横断検索コマンド、hit 件数、対象 rowIds、必要な spot screenshot を台帳に記録する。

代表確認を使える family 例:

- `dialog`
- `menu`
- `form-control`
- `titlebar-action`
- `list-card`
- `pagination`
- `video-control`
- `feedback-state`

family 内に実装差、viewport 差、操作差、文言差、アイコン差、enabled/disabled 差、副作用差、破壊的確認、URL 遷移、responsive 置換がある場合は、別 family または別代表バンドルへ分離する。

視認性、操作性、レイアウト崩れ、テキスト欠落、アイコン欠落に影響しない 1-3px の位置・寸法差だけを capture
tolerance として扱える。tolerance にする場合は、根拠 screenshot、DOM/geometry、却下理由を記録する。根拠のない tolerance は
`未確認` とする。

## データ同期

現行 UI と修正版 UI の比較は、必ず同一の API レスポンス、同一の現在時刻、同一のタイムゾーン、同一の設定値で行う。

- 比較に使う fixture、mock、DB スナップショット、API proxy 先を台帳に記録する
- 現在時刻依存表示は時刻を固定する
- ランダム値、現在時刻、実 API の更新タイミングで表示が変わる場合は、その行を `未確認` として扱う
- 日時、長さ、件数、容量、桁区切り、タイムゾーン依存表示は現行 UI と完全一致で比較する

生の実 API を使う場合でも、現行 UI と修正版 UI で同一レスポンスを使ったことを証明できない行は `未確認` とする。

## 必須確認範囲

以下の全ページと到達可能な全状態を確認する。

- ダッシュボード
- 放送中 / ライブ系ページ
- 番組表
- 番組表設定
- 録画中
- 録画済み一覧
- 録画詳細
- 動画再生 UI
- 予約一覧
- 予約詳細 / 編集
- 手動予約
- 検索
- ルール一覧
- ルール編集
- ストレージ
- アップロード
- エンコード
- 設定
- loading / empty / error / confirm / snackbar / toast / 404 状態

一覧アイテムでは、必ず以下を確認する。

- サムネイル / no image
- タイトル
- 説明 / 詳細テキスト
- 日時 / 時刻 / 長さ
- 放送局名と放送局 ID の取り違え
- ステータスラベル
- protect / skip / conflict / overlap などの状態
- タップ / クリック時の遷移
- 選択モード / 編集モード
- アイテムのメニューボタン
- アイテムメニューの中身

メニューでは、必ず以下を確認する。

- 現行 UI と同じ操作で開くか
- 項目名
- 項目順
- アイコン
- enabled / disabled
- 削除など破壊的操作の見た目
- 各項目を押した結果
- 外側クリック、Escape、キャンセル、ルート変更で閉じるか

メニューは、メニュー全体で 1 行にしてはいけない。開閉操作を 1 行、各メニュー項目を 1 行ずつ作る。各項目について、項目名、アイコン、順序、enabled/disabled、押下後の遷移または副作用、confirm の有無、閉じるタイミングを確認する。

見落としてはいけない例:

- 現行の録画済みアイテムメニューが、アイコン付きで `rule`, `search`, `protect`, `encode`, `delete` を出している。
- 修正版が `play TS` を出す、アイコンがない、順序が違う。
- これは、メニューが開いてページが壊れなくても UI 一致失敗である。

アイコンは「何か表示されている」だけでは一致扱いにしない。現行 UI と修正版 UI で、アイコンの種類、位置、サイズ、色、aria-label/title、アイコンのみボタンの accessible
name、disabled/hover/focus 時の見た目を比較する。

文言一致は、句読点、半角/全角、改行位置、敬体/常体、半角スペース、桁区切りまで完全一致を要求する。「ほぼ同じ」「意味は同じ」は不一致扱いにする。

順序一致は、項目順だけでなく、ソート規則、時系列の昇順/降順、五十音順、放送局順が現行 UI と一致することを確認する。データ件数を変えても順序が安定するか確認する。

ダイアログは、開く操作、タイトル、本文、各ボタン、初期フォーカス、Escape、外側クリック、キャンセル、確定、成功時、失敗時を個別行で確認する。confirm ダイアログでは、破壊的操作の文言、色、アイコン、実行前後の状態変化も確認する。

ダイアログ内の入力欄、バリデーションエラー、secondary
action、複数ステップ確認、成功/失敗後の snackbar/toast も個別行にする。

ページネーションは、コンポーネント全体で 1 行にしてはいけない。件数表示、現在ページ、prev、next、page
number、ellipsis、disabled、押下後 URL、スクロール位置、データ更新結果を個別に確認する。

レスポンシブ確認では、単に潰れや横スクロールを見るだけでなく、desktop と mobile で UI が置換される箇所を個別に確認する。例: サイドバーからドロワー、テーブルからカード、メニューから bottom
sheet、ヘッダ操作から overflow menu への変化。

確認する viewport は `desktop/tablet/mobile`
という名前だけでなく、プロジェクトで使う実ブレークポイント値を記録する。各ブレークポイントの直前・直後で、出現、消失、置換される UI を個別行にする。

## アクセシビリティとキーボード

全操作要素について以下を確認する。

- role、aria-label、aria-describedby、aria-expanded、aria-selected、aria-disabled
- Tab 順序、Shift+Tab、Enter、Space、Escape、矢印キー
- 初期フォーカス位置
- ダイアログ内の focus trap
- 閉じた後のフォーカス復帰位置
- アイコンのみボタンの accessible name

現行 UI と一致しない場合は差分行にする。

## テーマと言語

テーマ、言語、表示設定の切替が存在する場合は、それぞれ別行で確認する。切替機能が存在しない場合は、台帳の備考に「切替なし」と記録する。

- ライト / ダーク / システム連動テーマ
- 利用言語ごとの文言
- 半角/全角、日時、長さ、件数、容量のフォーマット
- 長文省略、折り返し、ellipsis、tooltip

## スクショと DOM 証跡

各ページ、各 viewport で以下を取る。

- 現行 UI と修正版 UI のページ全体スクショ。
- 各コンポーネント、メニュー、ダイアログの locator screenshot。
- 文言、aria-label、role、アイコンのみボタンが重要な箇所は DOM/アクセシビリティ情報。
- 比較時は、同じデータ、同じ route、同じ viewport、同じスクロール位置、同じ UI 状態にそろえる。

スクショだけでは不十分。アイコンのみボタンやメニューは、DOM/アクセシビリティ確認も併用する。

スクショは、network
idle、アニメーション/トランジション完了、Web フォント読み込み完了、DPR、拡大率、テーマ、言語、タイムゾーンを揃えて撮る。条件を揃えられない行は
`未確認` とする。

現行 UI のスクショが不足している場合は、修正作業を進める前に現行 UI の不足スクショを取得して保存する。現行 UI の証跡がない状態で、修正版 UI の見た目を「一致」「修正済み」と判断してはいけない。

現行 UI のスクショ取得は、原則として現行 UI をローカルまたは指定環境で起動し、修正版と同一データ、同一時刻、同一 viewport で撮る。現行 UI が消失して再取得できない場合は、過去成果物、staging、本番アーカイブなどの取得経路を備考に記録する。取得経路が確保できない行は
`未確認` とする。

証跡ファイル名またはディレクトリ名には、ページ、viewport、コンポーネント、要素、状態、操作を含め、台帳行から一意に対応できるようにする。

スクショとレビュー記録は、実 URL、実番組名、認証情報、cookie、session、個人環境の絶対パスを含む可能性があるため、原則として git
tracked file に保存しない。一時証跡ディレクトリを使い、tracked docs に記録する場合は placeholder 化し、secrets
scan を実行する。

## サブエージェントスクショレビュー

スクショ比較では、必ずサブエージェントにも同じスクショを見せ、同じ観点でレビューさせる。サブエージェントのレビュー結果は台帳またはレビュー記録に保存し、自分の比較結果と突合する。

サブエージェントに渡すスクショ:

- 現行 UI のページ全体スクショ
- 修正版 UI のページ全体スクショ
- 該当コンポーネント、メニュー、ダイアログ、ページネーションなどの locator screenshot
- 修正後に撮り直した修正版 UI のスクショ

サブエージェントに確認させる観点:

- 文言、アイコン、順序、件数
- 位置、サイズ、余白、色、フォント、シャドウ、角丸
- disabled、selected、focus、hover
- メニュー項目名、アイコン、順序、押下結果
- ダイアログのタイトル、本文、ボタン、閉じ方
- ページネーション、FAB、MORE、snackbar/toast
- レスポンシブ時の置換 UI

サブエージェントには、比較対象、画像パス、現在の台帳行、確認観点、出力形式を明示して依頼する。画像ファイルに実 URL、実番組名、認証情報、cookie、session、個人環境の絶対パスが含まれる可能性がある場合は、tracked
file に保存せず、一時証跡ディレクトリの範囲だけを渡す。

サブエージェントへの指示には以下の出力形式を必ず含める。

- 各差分に通し番号を付ける
- 画像 A、つまり現行 UI を基準に、画像 B、つまり修正版 UI で `不足` / `余分` / `不一致` のどれかを明示する
- 観点: 文言、アイコン、順序、位置、サイズ、余白、色、状態、アクセシビリティを付ける
- 重大度: 致命 / 重要 / 軽微を付ける
- 比較した画像パスを記録する
- 画像の解像度または画面名を記録する
- サブエージェントが画像内容から読み取った主要 UI 要素を記録する

台帳にはサブエージェント指摘の通し番号と台帳行 ID の対応表を保存する。

サブエージェントが差分を指摘し、自分の台帳にない場合は、その差分を台帳に追加する。サブエージェントが誤認した可能性がある場合でも、必ず自分でスクショ、DOM、アクセシビリティ情報を再確認し、採用/却下理由を記録する。

サブエージェントレビューなしで「スクショ比較済み」と言ってはいけない。サブエージェントが使えない場合は、その理由、試した代替確認、代替レビュー方法を記録し、該当行を
`未確認` とする。

サブエージェントレビューの未実施は `対象外` にしてはいけない。サブエージェントが使えない行は `未確認`
のままとし、完了報告は禁止する。ユーザーが明示的にサブエージェントレビュー不要と指示した場合でも、この skill に基づく完了表現は使わず、「サブエージェントレビュー未実施のため未完了」と報告する。

サブエージェントのレビュー結果が「画像を確認できない」「読み取れない」「アクセスできない」旨を含む場合、または出力が空、極端に短い、画像パス名だけから推測した内容に見える場合は、レビュー成立としない。該当行を
`未確認` とし、再実行する。再実行も失敗した場合はサブエージェント失敗時の手順に従う。

サブエージェント実行時は必要最小限の画像と台帳だけを渡す。対象画像に秘密情報が含まれる可能性がある場合は、redact した画像または要約した locator
screenshot を使う。

## 修正後の再スクショ比較

修正後は、必ず同じ route、viewport、スクロール位置、データ、UI 状態で修正版 UI のスクショを撮り直す。修正前スクショや目視記憶で再確認したことにしてはいけない。

再比較では以下を行う。

- 現行 UI スクショと修正後スクショを並べて比較する
- 修正対象の locator screenshot も撮り直す
- DOM/アクセシビリティ情報も必要に応じて取り直す
- サブエージェントに修正後スクショと現行スクショを再レビューさせる
- 修正前に記録した差分が消えたか確認する
- 新しい差分が発生していないか確認する

自分の再比較またはサブエージェントの再レビューで差分指摘が 1 件でも残る場合は、再度修正し、再度スクショを撮り直し、同じ現行 UI スクショと再比較する。このループは、自分の指摘とサブエージェントの指摘が 0 件になるまで必ず繰り返す。

各ループで以下を記録する。

- ループ番号
- 修正内容
- 撮り直したスクショパス
- 自分の再比較結果
- サブエージェントの再レビュー結果
- 残差分件数
- 新規差分件数

差分指摘が残っている状態で `再確認済み`
にしてはいけない。サブエージェントの指摘を却下する場合は、スクショ、DOM、アクセシビリティ情報に基づく却下理由を記録し、却下後の残差分件数を 0 にする。

サブエージェントの同一指摘を 2 回以上却下した行、または同一行で却下が累計 3 件を超えた行は、当該タスクを実装したエージェント自身ではない承認者の確認を必須とする。承認者名、承認日時、却下理由、根拠証跡を備考に記録する。自己承認による却下は
`未確認` 扱いとする。

修正後スクショとサブエージェント再レビュー結果がない行は `再確認済み` にしてはいけない。

## 状態と操作の確認

全ての操作要素について、以下を確認する。

- 押下前
- 押下後
- close / cancel
- confirm / apply
- success
- failure / error
- disabled 状態
- selected / focused / hover: 見た目に意味がある場合

操作可能要素は原則として focus と hover も確認する。確認しない場合は、見た目に意味がない根拠を備考に書く。

押下後は、URL、history stack、戻るボタン、リロード後の状態保持、スクロール位置、snackbar/toast の有無も確認する。

作れない状態は削除せず、台帳に `未確認`
と書く。作れない理由、試した再現方法、必要な mock/fixture/API 条件、残作業を記録する。未確認を残したまま完了報告してはいけない。

failure / error 状態は、原則として mock、fixture、API
intercept、またはテスト用データで生成する。「手元で自然発生しなかった」だけでは確認不要にしてはいけない。生成できない場合は
`未確認` とし、必要な mock/API 条件と残作業を記録する。

failure / error は、HTTP 400 / 401 / 403 / 404 / 409 / 422 / 500 / 503 / timeout /
offline を、該当機能で意味がある範囲で生成して確認する。

snackbar/toast は、出現位置、表示時間、複数同時表示、閉じる操作、aria-live、重複発火の有無を確認する。

## 同種 UI の横断検索

1 箇所を修正したら、同じ種類の UI を検索して確認する。

```bash
rg -n "Menu|menu|IconButton|Pagination|Dialog|Snackbar|Toast|MORE|more|protect|encode|delete|rule|search" client/src
```

記録する内容:

- 実行したコマンド
- 該当ファイル
- 同種 UI と判断した箇所
- 確認済み箇所
- 修正が必要な箇所
- hit 件数
- 台帳化した件数

最初に指摘されたページだけを直して終わってはいけない。

## テスト要件

存在確認だけのテストでは不十分。

テストでは以下を確認する。

- メニュー項目名、順序、アイコン、件数
- 現行 UI にない `play TS` などの文言が出ていないこと
- 同じ操作でダイアログが開き、同じアクションが存在すること
- ページネーションの位置、ボタン、disabled、ラベル/アイコン、押下後 URL
- レスポンシブ表示で潰れや横スクロールがないこと
- 現行 UI と同じ条件で、モバイルナビやメニューが外側クリックで閉じること

使うテスト種別:

- Playwright E2E: 実操作確認
- visual / geometry test: レスポンシブと配置確認
- unit test: route やデータ変換確認
- DOM / accessibility assertion: メニューやアイコンボタン確認

## 完了ゲート

完了と言う前に、必ず以下を報告する。

- 台帳のパス
- スクショ/証跡ディレクトリ
- 確認したページ数
- 確認した要素行数
- 開いたメニュー数
- 確認したメニュー項目数
- 開いたダイアログ数
- 現行 UI スクショ数
- 修正版 UI スクショ数
- 修正後に撮り直したスクショ数
- サブエージェントスクショレビュー実施件数
- サブエージェント指摘から台帳に追加した差分数
- 修正後再比較ループ回数
- 最終ループでの自分の残指摘件数
- 最終ループでのサブエージェント残指摘件数
- 発見した差分数
- 修正した差分数
- 未着手行数
- 現行確認済み止まりの行数
- 修正版確認済み止まりの行数
- 修正中行数
- 修正済み(未再確認)の行数
- 未確認行数
- 未解決行数
- 対象外行数と理由
- rg 横断検索の hit 件数
- rg 横断検索の台帳化件数
- 実行したコマンド
- テスト結果

許可する完了表現:

- 台帳の全行が `再確認済み` または承認済みの `対象外` であり、`未着手 = 0`, `現行確認済み = 0`, `修正版確認済み = 0`,
  `差分あり = 0`, `修正中 = 0`, `修正済み(未再確認) = 0`, `未確認 = 0`, `未解決 = 0`
  かつ、route 定義、ナビ、リンク、条件付き表示、同種 UI 横断検索から発見した対象がすべて台帳化され、rg 横断検索の hit 件数と台帳化件数が一致し、サブエージェントスクショレビュー実施件数が台帳の比較対象行数以上であり、現行 UI スクショ、修正後スクショ、サブエージェントスクショレビュー結果がすべて台帳行に 1:1 で紐づき、最終再比較ループで自分の残指摘件数とサブエージェントの残指摘件数がどちらも 0 の場合だけ: 「発見済み全範囲について完了」
- それ以外: 「未完了」とし、残り行を列挙する

確認対象外にする行がある場合は、ステータスを `対象外`
とし、対象外理由、根拠、代替確認方法、当該タスクを実装したエージェント自身ではない承認者の名前と承認日時を備考に記録する。理由や承認のない
`対象外`、自己承認の `対象外` は `未確認` と扱う。

禁止する完了表現:

- 件数なしの「全部確認済み」
- 台帳証跡なしの「漏れなし」
- build/test が通っただけの「修正済み」
- 「見た目は近い」
- 「代表ページは通った」
- 「サンプル確認」
- 「抜き取り確認」
- 「主要箇所は確認」
- 「だいたい」
- 「ざっくり」
- 「概ね」
