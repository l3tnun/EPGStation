# Serverソースコメント方針

## 目的

`src/**`（server）では、関数の説明、引数（型含む）、戻り値（型含む）、追加された class の private
member 変数にコメントが無いと、実装の意図が読めない。export された関数・class・interface・type の
うち説明コメントが付いているものの割合は低く（v2 base で 8.8%、v3 で新規に書かれた file では 5.0%）、
書き方も統一されていない（v2 は一部で `@param` / `@return` タグを使い、v3 の新規コメントはタグ無しの
自由記述）。この文書は、`src/**` へコメントを書く・見直す際の統一規約を定め、この不一致を防ぐ。

適用範囲は `src/**` のみ。`client/**` は対象外（`client-is-not-product-code` の扱いと同じく、v3の
`client/**` は product code ではない）。

この書式は、新規に書くコメントと変更するコメントに適用する。既存のコメント（`@return` を使うものを含む）は、
その箇所を変更しないかぎり一括では書き換えない。

## 形式: JSDoc + `@param` / `@returns` タグを使う

- 関数・method・class・interface の説明は `/** ... */` の JSDoc block とする。行末 `//` の単発コメントは
  private member 変数や型 alias の 1 行説明など、JSDoc block を書くほど分量が無い箇所にのみ使う。
- 関数・method には本文の説明文に加えて、引数ごとに `@param 名前 説明`、戻り値がある場合は
  `@returns 説明` を付ける。`void` の場合は `@returns` を省略してよいが、副作用がある場合は本文の説明に
  含める。
- **タグの説明文で型そのものを言葉にして繰り返さない**（例: `@param port ポート番号（number）` のような
  記述は禁止）。型は TypeScript のシグネチャに既に書かれており、JSDoc タグはシグネチャの数行内に
  必ず隣接して表示される。タグが担うのは「その型の値が何を意味するか」「取りうる特殊値
  （`null` / `undefined` / 空配列などがある場合にそれが何を表すか）」であり、型名の言い換えではない。

### なぜこの形式にしたか

- Owner は「引数（型含む）、戻り値（型含む）」を明示的に要求している。TypeScript では型はシグネチャに
  既にあるため、コメント本文で型を文章化する必要は無い。一方で `@param` / `@returns` タグは、
  引数名・戻り値をシグネチャの型定義とセットで指し示す固定の位置を持ち、「どの引数の話をしているか」
  「戻り値についての説明かどうか」を読み手が機械的に対応付けられる。これは prose 一本槍
  （現状の v3 の書き方）では保証されない。
- v2 は一部の method で既に `@param` / `@return` タグを使っていた（`V1MigrationTool.ts` 等）。
  タグ無しの新形式を今から始めるより、既存の部分的な precedent に揃える方が、file 内でスタイルが
  混在する箇所を減らせる。
- 逐語訳（型の言い換え）を明示的に禁止することで、「タグを埋めるためだけに機械的な一言を書く」という
  劣化（このリスクはタグ形式特有の弱点）を防ぐ。

## 日本語で書く

- コメントは日本語で書く。既存 steering document（本 file を含む全て）と、調査で「説明として機能して
  いる」と判定された既存コメント実例（`pathParam`、`LiveHLSStreamModel` 等、いずれも日本語）は日本語で
  あり、少数派の英語コメントより多数派の日本語に揃える。
- コード中の識別子（class 名、property 名、library 名等）は原語のまま記述してよい。

## 何を書くか

- **関数・method・class・interface・type の説明**: 名前の言い換えではなく、呼び出し側から見た役割
  （何のために存在するか）。同じ module 内の他の宣言と役割がどう違うかが分かるように書く。
- **引数の意味**（`@param`）: 型ではなく、どんな値が来る前提か、単位、取りうる特殊値
  （`null` / `undefined` / 空配列 / 空文字の意味）。
- **戻り値の意味**（`@returns`）: 成功・失敗をどう表現するか（例外を投げるか、`null` を返すか）。
  `void` で副作用がある場合はその副作用を本文に書く。
- **前提条件・不変条件**: 呼び出し順序の制約、事前に呼ぶべき初期化、状態を持つ class の状態遷移。
- **追加された class の private member 変数**: 何を保持するか、いつ・何によって値が変わるか
  （constructor 時のみ固定か、特定の method 呼び出しで更新されるか）。
- **非自明な理由**: 読んだだけでは分からない罠、外部 library・runtime の制約による回避策
  （例: InversifyJS の decorator 継承の制約）。
- 実装から意図を読み取れない箇所は、推測で書かない。「この関数の意図は実装から読み取れなかった」と
  作業記録に残し、Owner に確認する。

## 何を書かないか

- コードをそのまま読み上げただけの逐語訳（`/** Logger */` のような class 名の反復、
  `/** 予約オプションチェッカー */` のような class 名の直訳)。
- 型定義から自明な情報の反復（`port?: number` に対して「port 番号」とだけ書く）。
- 実装の逐行説明（`// i を 1 増やす` のような、コードを読めば一目で分かる説明）。

## 対象と優先順位

- 対象は v2 base（`5cf2ea383`）以降に `src/**` で追加・変更された file とする。この範囲より前から
  存在し、変更していない file は、対応する機能に手を入れる際に併せて見直す。
- 優先順位は次の順とする。
  1. export 数が多く comment 付与率 0 の file（`I*.ts` interface 定義を含む）。
  2. 新規追加 file（付与率が最も低い区分）。
  3. 大規模な変更 file（1 file が大きい場合は 1 file を複数 commit に分割してよい）。
- 1 commit の diff はコメント行の追加のみに限定し、コードの修正・リネーム・整形を混在させない。
